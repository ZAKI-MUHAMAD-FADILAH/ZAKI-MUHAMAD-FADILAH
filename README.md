## `03 // ENGINEERING DOCTRINE`

| Principle | What it means in practice | Failure mode it fights |
| :--- | :--- | :--- |
| 🛡️ **Secure by design** | Threat model first; least privilege; explicit trust boundaries | Security bolted on after launch |
| 📐 **Scalable by design** | Clear domains; stateless services; queues where asynchronous work belongs | Fragile monoliths and blocking workloads |
| 🔭 **Observable by default** | Structured logs; correlation IDs; metrics; audit events | "It failed" without evidence |
| ♻️ **Idempotent automation** | Deduplication keys; safe retries; replayable jobs; dead-letter paths | Duplicate writes and retry storms |
| 💸 **Cost-aware infrastructure** | Measure before scaling; cache intentionally; right-size compute | Expensive architecture without leverage |
| 🧠 **Guardrailed AI** | Structured outputs; evaluation; policy checks; human escalation | Confident but unsafe automation |

​
PERFORMANCE WITHOUT SECURITY         = LIABILITY
SECURITY WITHOUT USABILITY           = BYPASS
AUTOMATION WITHOUT IDEMPOTENCY       = INCIDENT
AI WITHOUT GUARDRAILS                = UNCONTROLLED RISK

## `05 // SECURITY CONTROL PLANE`

| Layer | Controls I design for | Security property |
| :--- | :--- | :--- |
| **Identity** | MFA, secure sessions, rotation, recovery controls | Strong authentication |
| **Authorization** | RBAC, RLS, ownership checks, deny-by-default policies | Least privilege |
| **Application** | Schema validation, output encoding, rate limiting, safe errors | Reduced attack surface |
| **Data** | Scoped queries, encryption boundaries, retention, immutable audit events | Confidentiality and integrity |
| **Delivery** | Dependency review, secret scanning, container hardening, protected CI/CD | Trusted releases |
| **Operations** | Central logs, alerts, anomaly review, backups, tested recovery | Detection and resilience |

<details>
<summary><b>▸ Open secure-delivery checklist</b></summary>

### Before implementation

- Identify assets, actors, entry points, trust boundaries, and abuse cases.
- Define authentication, authorization, data classification, and retention rules.
- Design failure behavior, recovery paths, and evidence needed during an incident.

### During implementation

- Validate at every boundary and keep authorization server-side.
- Make sensitive mutations idempotent, auditable, and transactionally safe.
- Keep secrets out of source control, logs, client bundles, and error responses.
- Add negative tests for role, tenant, ownership, replay, and rate-limit boundaries.

### Before release

- Run automated checks, dependency review, security tests, and rollback rehearsal.
- Verify logs contain useful context without credentials or sensitive payloads.
- Confirm alerts are actionable and backups can actually be restored.

</details>

<a id="build-protocol"></a>

## `06 // BUILD PROTOCOL`

<details open>
<summary><b>▸ From idea to hardened production</b></summary>

<br />

​
flowchart LR
A["Discover"] --> B["Threat Model"]
B --> C["Design"]
C --> D["Build"]
D --> E["Verify"]
E --> F["Automate"]
F --> G["Observe"]
G --> H["Harden"]
H --> B
E -->|failure| D
G -->|incident evidence| B

1. **Discover** the real operational problem and define measurable outcomes.
2. **Threat model** assets, actors, boundaries, abuse paths, and stop conditions.
3. **Design** contracts, data ownership, failure modes, observability, and recovery.
4. **Build** the smallest secure vertical slice with explicit invariants.
5. **Verify** happy paths, negative paths, authorization, concurrency, and replay.
6. **Automate** repeatable delivery, checks, migrations, and operational workflows.
7. **Observe** behavior through logs, metrics, traces, audit events, and user signals.
8. **Harden** continuously using evidence from production and adversarial testing.

</details>
